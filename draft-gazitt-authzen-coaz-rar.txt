Abstract

   This specification defines COAZ-RAR, the COAZ binding, as defined by
   the COAZ Framework [COAZFW], for OAuth 2.0 Rich Authorization
   Requests [RFC9396].  An authorization details type is typically
   defined by one party and processed by others: an authorization server
   decides whether to grant an entry of that type, and a resource server
   decides whether a call is permitted under it.  This binding lets the
   definer of a type publish, once, how an entry of that type maps onto
   an OpenID AuthZEN Authorization API request [AUTHZEN], and lets both
   enforcement points apply that mapping.  The authorization server
   applies it at token issuance, under the AuthZEN profile for OAuth 2.0
   token issuance [ISSUANCE]; the resource server applies it when a call
   arrives.  Both ask the Policy Decision Point their questions in one
   vocabulary.  The mapping is published as a member of the type's entry
   in the authorization details types metadata defined by [RARMETA].

1.  Introduction

   Rich Authorization Requests [RFC9396] let a client ask for
   structured, fine-grained access: a payment to a named creditor for a
   stated amount, read access to one patient's records, a set of file
   paths.  Each entry in an authorization_details array has a type, and
   the type determines which members the entry may carry and what they
   mean.

   A type is usually defined by someone other than the authorization
   server (AS) that processes it.  Open banking and health ecosystems
   define types that many servers must handle, which is why Section 2.1
   of [RFC9396] recommends collision-resistant type names for APIs
   "expected to be deployed across different servers."  The resource
   server (RS) whose API a type describes is another definer.  So is a
   Model Context Protocol [MCP] server, whose tool input schemas are
   type definitions in all but name.

   RFC 9396 leaves the decision to grant an entry, and the RS's decision
   on a call made under it, to each server.  Two pieces of adjacent work
   narrow that gap from different sides:

   *  The AuthZEN profile for OAuth 2.0 token issuance [ISSUANCE] lets
      an AS externalize the issuance decision to a Policy Decision Point
      (PDP).  It decomposes an entry along RFC 9396's common data fields
      (locations, actions, datatypes) and asks one question per cell.
      It does not decompose identifier, privileges, or any type-specific
      member, so for a type whose meaning lives in its own members, such
      as the creditor and amount of a payment, the PDP never sees what
      the decision is about.

   *  [RARMETA] defines an AS metadata endpoint that publishes a JSON
      Schema for each type, and a challenge with which an RS that
      refuses a call tells the client exactly which entry to request.

   Neither says how an entry of a given type becomes an authorization
   question.  The party that knows is the type's definer.  The COAZ
   Framework [COAZFW] exists for exactly this split between a party that
   describes an operation and a party that enforces it: COAZ-MCP
   [COAZMCP] lets an MCP server declare, in a tool's input schema, how a
   call to that tool maps onto an AuthZEN request, so that a gateway
   with no knowledge of the server's business logic can enforce it.

   This specification is COAZ-RAR, the COAZ binding for authorization
   details.  It treats an authorization details type as the operation
   description, and the types metadata of [RARMETA] as the place a
   mapping is published.  Two enforcement points apply it:

   *  The AS, at issuance, for each cell of each requested entry, in
      place of the per-cell projection of [ISSUANCE].

   *  The RS, when a call arrives, for the entry the call amounts to.

   Because both apply the same mapping, both ask the PDP in one
   vocabulary.  Where the entry names a specific resource, as it does
   when the RS built it from a call it refused, the AS and the RS ask
   the same question.  Where it doesn't, as with a standing grant, the
   AS asks about the class of resource and the RS asks about the member
   of it that the call touches.

1.1.  Requirements Notation and Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

1.2.  Terminology

   This specification uses the terms defined in the COAZ Framework
   [COAZFW], notably binding, information model, input variable,
   mapping, literal, expression, default mapping, declared mapping, PEP,
   and PDP, and the terms authorization details, authorization details
   type, and common data fields defined by [RFC9396].  It adds the
   following:

   Entry:  One object in an authorization_details array.

   Cell:  One combination of a locations value, an actions value, and,
      where present, a datatypes value of an entry.  Section 2.2 of
      [RFC9396] defines an entry as the product of these values; a cell
      is one element of that product.

   Type Definer:  The party that defines an authorization details type
      and its meaning: an ecosystem, a resource server operator, or an
      MCP server.

   Issuance PEP:  The AS, acting as a PEP when it decides whether to
      grant an entry under [ISSUANCE].

   Resource PEP:  The RS, or a gateway in front of it, acting as a PEP
      when it decides whether to permit a call.

   Projection:  The entry and cell that an RS determines a call amounts
      to.

   Prospective Token:  The set of claims the AS will place in the access
      token it is about to issue, as known before the PDP is asked.

               Figure 1: One mapping, two enforcement points

   1.  The client calls the RS with a token that does not cover the
       call.

   2.  The RS projects the call onto an entry and answers with the
       remediation challenge of [RARMETA], carrying that entry.

   3.  The client requests a token for the entry.

   4.  The AS applies the type's mapping to each cell of the entry and
       asks the PDP, under [ISSUANCE].  It issues a token for what the
       PDP permits.

   5.  The client retries the call with the new token.

   6.  The RS applies the same mapping to its projection of the call and
       asks the PDP before permitting it.

   Steps 1 and 2 are absent when a client requests an entry without
   having been refused, as with a standing grant.  Step 6 occurs on
   every call the token covers, whether or not the entry came from a
   remediation.

   The PDP at step 4 and the PDP at step 6 need not be the same.  In a
   cross-domain deployment the AS's PDP holds the policy of the
   organization whose user or agent is asking, and the RS's PDP holds
   the policy of the organization that owns the resource.  The mapping
   gives them a common vocabulary without requiring a common policy.

3.  Information Model

   This binding exposes four input variables to expressions.  Each is
   populated differently at the two enforcement points.

     +==========+============================+======================+
     | Variable | At the Issuance PEP        | At the Resource PEP  |
     +==========+============================+======================+
     | detail   | The entry being evaluated, | The entry of the     |
     |          | after any enrichment by    | projection           |
     |          | the AS (Section 3.4)       | (Section 3.2)        |
     +----------+----------------------------+----------------------+
     | cell     | The cell being evaluated   | The cell of the      |
     |          | (Section 3.1)              | projection           |
     +----------+----------------------------+----------------------+
     | token    | The prospective token      | The claims of the    |
     |          | (Section 3.3)              | presented access     |
     |          |                            | token                |
     +----------+----------------------------+----------------------+
     | params   | {"name": <type>,           | The same, or the MCP |
     |          | "arguments": <detail>}     | params object where  |
     |          |                            | the Resource PEP is  |
     |          |                            | an MCP gateway       |
     +----------+----------------------------+----------------------+

                                 Table 2

   detail:  A map holding the entry, with every member it carries,
      including type.

   cell:  A map with a location key (string), an action key (string), a
      datatype key (string) that is present only when the cell has a
      datatype, and a name key (string) holding the action name
      [ISSUANCE] forms for the cell: the action alone, or the action and
      datatype joined by a colon.

   token:  A map of access token claims.  At the Resource PEP these are
      the decoded claims of a JWT access token [RFC9068] or the members
      of a token introspection response [RFC7662].

   params:  A map holding the operation's name and arguments in the
      shape COAZ-MCP [COAZMCP] exposes for tools/call.  It exists so
      that a mapping written for an MCP tool runs unchanged when that
      tool is also used as an authorization details type (Section 8.4).

3.1.  Cells

   At the Issuance PEP, the cells of an entry and their order are those
   of the Authorization Detail Tuple section of [ISSUANCE], including
   its substitutions for absent members: an absent locations takes each
   requested target, an absent actions takes the reserved name
   authorization_detail, and an absent datatypes yields cells without a
   datatype key.  This binding does not change how many cells an entry
   has; it changes only how each cell becomes evaluations.

   At the Resource PEP, the cell is the location, action, and datatype
   that the call occupies, in the type's own vocabulary.

3.2.  The Resource PEP's Projection

   A Resource PEP MUST be able to project each call it authorizes under
   this binding onto an entry and a cell.  The entry's type is the type
   that describes the call, and its other members are the values the
   call supplies for that type's members.

   Where a call addresses a specific resource and the type allows
   identifier (Section 2.2 of [RFC9396]: "a specific resource available
   at the API"), the projection MUST set identifier to that resource.
   This is what lets a mapping ask about the instance at the RS while
   the AS, given an entry without an identifier, asks about the class
   (Section 8.3).

   The projection is also the basis of the remediation entry of
   [RARMETA], which that document says is "built using the failed
   resource request."  A Resource PEP that issues a remediation
   challenge SHOULD construct its entry from the projection, adding
   locations, actions, and datatypes from the cell only where the type's
   schema allows those members.  Building the remediation from the
   projection is what makes the AS evaluate, at issuance, the question
   the RS will ask when the call is retried.

3.3.  The Prospective Token

   At issuance there is no token yet.  The Issuance PEP binds token to
   the claims it will place in the token it is about to issue: at least
   sub, client_id, and aud, and any other claim it will mint that does
   not depend on the PDP's response.  Claims that the PDP's response
   would add, such as those of the claims key of [ISSUANCE], are not
   available.

   A mapping intended for both enforcement points MUST use optional
   selection (.?) for any claim other than sub, so that an AS that does
   not mint the claim produces an absent value rather than a mapping
   error.

3.4.  Enrichment

   Section 7.1 of [RFC9396] allows an AS to enrich an entry with values
   the user selects during the interaction, such as a specific record.
   At the Issuance PEP, detail MUST be the entry after enrichment.  A
   mapping that selects a member the client did not send, such as
   identifier, would otherwise fail on every request from a client that
   relies on enrichment.

4.  Expressions and Literals

   This binding uses the framework's defaults unchanged: expressions are
   written in CEL [CEL], a string value beginning with $ is an
   expression, and $$ escapes a literal $. An expression yields *absent*
   by CEL optional selection or by optional.none(), and the containing
   member is omitted.

   Every mapping in this binding, including the default, contains
   expressions, so a conforming PEP MUST include a CEL evaluator.  An
   Issuance PEP SHOULD compile a type's mapping when it adopts the type
   (Section 6) rather than per request.

5.  Mapping Envelopes

   This binding permits both envelope keys defined by the framework:

   *  evaluation, for a cell that needs one decision.  The default
      mapping uses it, and it is RECOMMENDED for declared mappings that
      need one decision.

   *  evaluations, for a cell that needs several, such as a transfer
      that must be authorized both as a debit of the source account and
      as a payment to the payee.  The evaluations array MUST be a
      literal array; an expression in its place is a mapping error, as
      Section 2.6 of [COAZFW] requires.

   Any other envelope key is a mapping error.

5.1.  Operations in Scope

   The COAZ operation for this binding is *one cell of one entry*. A
   mapping is applied once per cell, and the cell is permitted only if
   every evaluation the mapping produces for it is a permit, which is
   the fail-closed rule of the framework applied to the cell.

   At the Issuance PEP, the number of cells is set by the entry and by
   [ISSUANCE], not by the mapping.  That is how this binding keeps the
   number of decisions fixed by the envelope, as the framework requires,
   while an entry still yields as many questions as its product
   contains.  How the cells of an entry combine into what is granted,
   and what the AS does when some are denied, is defined by [ISSUANCE]
   ("A Denied Cell Narrows an Entry") and is outside this binding.

   There is no pass-through set.  Every cell of every entry is
   authorized.  An entry whose type the AS does not support is rejected
   under Section 5 of [RFC9396] before any mapping is selected.

6.  Declaring a Mapping

   A type's mapping is published in the response of the
   authorization_details_types_metadata_endpoint of [RARMETA], as a
   member of the object describing that type:

   authzen_mapping:  OPTIONAL.  A COAZ mapping, as defined by [COAZFW]
      and constrained by this binding, for entries of this type.

   A PEP selects the mapping for a type as follows:

   1.  If the type's metadata object has an authzen_mapping member, use
       it.

   2.  Otherwise, if the type's schema (or the document at its
       schema_uri) has an x-authzen-mapping member at its top level, use
       it.  This is where COAZ-MCP places a tool's mapping, so a tool's
       input schema adopted as a type's schema brings its mapping with
       it.

   3.  Otherwise, use the default mapping (Section 7).

   The mapping is authored by the type definer and *adopted* by the AS
   operator, in the same act by which the AS adopts the type's schema
   today.  An AS that adopts a type with a declared mapping takes on
   that mapping as configuration; it does not fetch a mapping from a
   type definer at request time.  A Resource PEP obtains the mapping
   from the same types metadata, so that both enforcement points apply
   the mapping the AS adopted.

   The types metadata endpoint is not access-controlled.  Publishing a
   mapping there discloses which members of a type the policy considers,
   which is the shape of the authorization question and not the policy
   that answers it.  An AS that considers even that shape sensitive can
   omit authzen_mapping from the published metadata and provision the
   Resource PEP with it by other means.

7.  Default Mapping

   Where a type declares no mapping, a PEP applies the following default
   to each cell.  It is the per-cell projection of the Authorization
   Detail Tuple section of [ISSUANCE], expressed as a COAZ mapping:

   {
     "evaluation": {
       "action": { "name": "$cell.name" },
       "resource": { "type": "$detail.type", "id": "$cell.location" }
     }
   }

                       Figure 2: The default mapping

   The subject and the top-level context are supplied by the PEP: by
   [ISSUANCE] at the Issuance PEP, and from the presented token at the
   Resource PEP (Section 8).  Where [ISSUANCE] declines to compound a
   datatype into an action name (a datatypes value containing a colon),
   cell.name is the action alone.

   The default asks about the location, so it aligns the two enforcement
   points at the level of the class of resource only.  A type that needs
   the RS to ask about a specific resource declares a mapping
   (Section 8.3).

8.  Declared Mappings

   A type definer MAY declare a mapping for a type.  A declared mapping
   overrides the default for every cell of every entry of that type, and
   for no other type.

   subject.id is trust-anchored, enforced by verification.  A declared
   mapping MAY set subject.id; if it does, it MUST set it to $token.sub,
   and the PEP MUST verify that the resolved value equals the
   authenticated subject: at the Issuance PEP, the subject [ISSUANCE]
   places in the request; at the Resource PEP, the sub claim of the
   presented token.  A mismatch is a mapping error.  If a declared
   mapping omits subject or subject.id, the PEP supplies them as it
   would for the default mapping.

   A declared mapping using the evaluations envelope MUST NOT set
   subject in any entry of its evaluations array; a PEP MUST treat one
   that does as a mapping error.

   Every attribute a declared mapping supplies other than the verified
   subject.id, including subject.type and every properties member, is
   untrusted input under Section 2.9 of [COAZFW].  A policy that grants
   on the basis of an elevated role or privilege MUST rely on the
   verified subject.id, not on a declared subject.type.

8.1.  Payment Initiation

   The payment_initiation type of RFC 9396 Figure 2.  The decision is
   about the creditor and the amount, both type-specific members that
   the default mapping does not reach.  The declared mapping puts the
   creditor in the five-tuple and the amount, a parameter of the act, in
   action.properties:

   {
     "evaluation": {
       "action": {
         "name": "$cell.action",
         "properties": {
           "amount": "$detail.instructedAmount.amount",
           "currency": "$detail.instructedAmount.currency"
         }
       },
       "resource": {
         "type": "creditor_account",
         "id": "$detail.creditorAccount.iban"
       },
       "context": { "agent": "$token.?client_id" }
     }
   }

            Figure 3: A declared mapping for payment_initiation

   A mapping can branch per action where actions concern different
   entities; a cancel cell, for instance, might be asked about the
   payment rather than the creditor.  The CEL conditional operator
   serves for that, as COAZ-MCP's examples show.

   For the initiate cell of the Figure 2 entry, the Issuance PEP
   produces:

   {
     "action": {
       "name": "initiate",
       "properties": { "amount": "123.50", "currency": "EUR" }
     },
     "resource": {
       "type": "creditor_account",
       "id": "DE02100100109307118603"
     },
     "context": { "agent": "fintech-app" }
   }

   When the client retries POST /payments with the token, the Resource
   PEP projects the request body onto the same entry and produces the
   same evaluation.

8.2.  Two Decisions per Cell

   A transfer type with no common data fields at all, so each entry is a
   single cell with the substituted action authorization_detail.  The
   mapping ignores that action and asks two questions:

   {
     "evaluations": {
       "context": { "agent": "$token.?client_id" },
       "evaluations": [
         {
           "action": {
             "name": "debit",
             "properties": {
               "amount": "$detail.instructed_amount.amount",
               "currency": "$detail.instructed_amount.currency"
             }
           },
           "resource": {
             "type": "account",
             "id": "$detail.debtor_account.account_id"
           }
         },
         {
           "action": {
             "name": "pay",
             "properties": {
               "amount": "$detail.instructed_amount.amount",
               "currency": "$detail.instructed_amount.currency"
             }
           },
           "resource": {
             "type": "pix_key",
             "id": "$detail.creditor_account.pix_key"
           }
         }
       ]
     }
   }

          Figure 4: A declared mapping with two decisions per cell

8.3.  Class and Instance

   The customer_information type of RFC 9396 Figure 5, with identifier
   allowed.  A client requesting a standing grant sends no identifier; a
   call to GET /customers/c-77/contacts names one.  The mapping asks
   about the collection in the first case and about the customer in the
   second:

   {
    "evaluation": {
     "action": { "name": "$cell.name" },
     "resource": {
      "type":
       "$has(detail.identifier) ? 'customer' : 'customer_information'",
      "id":
       "$has(detail.identifier) ? detail.identifier : cell.location"
     }
    }
   }

                Figure 5: One mapping, two levels of detail

   At issuance the PDP is asked read:contacts on
   customer_information:https://example.com/customers, which today's
   policy may answer by role.  At the RS it is asked read:contacts on
   customer:c-77, which a policy may answer by the subject's
   relationship to that customer.  The policy can move from the first
   answer to the second without either enforcement point changing,
   because the RS was asking about the instance all along.  A PDP that
   does not hold the relation between a customer and the collection can
   be given it by the mapping, as a resource property set only when
   identifier is present.

   A token granted on the class does not cover every instance.  A call
   about a customer the subject has no relationship with is refused by
   the Resource PEP's own evaluation, even though the token covers the
   call.  When an RS remediates a refused call (Section 3.2), the entry
   carries the identifier, and the AS asks about the instance as well.

8.4.  MCP Tools as Authorization Details Types

   An MCP tool can be used as an authorization details type: its type is
   a URI naming the tool, its members are the tool's arguments, and its
   schema is the tool's input schema.  If that input schema carries a
   COAZ-MCP x-authzen-mapping, step 2 of Section 6 selects it, and the
   params variable lets it run unchanged: params.arguments is the entry
   at the Issuance PEP and the tools/call arguments at an MCP gateway,
   and token.sub is the authenticated subject at both.

   An MCP gateway that refuses a tools/call can therefore remediate with
   an entry built from the call's arguments, and the AS evaluates, at
   issuance, the call the gateway will see on retry.  This gives
   issuance a decision on the concrete arguments of a specific call,
   which it otherwise does not have.

9.  PEP Behavior

9.1.  Issuance PEP

   When an AS processes a token request carrying authorization_details
   under [ISSUANCE], it MUST, for each entry:

   1.  Apply any enrichment (Section 3.4).

   2.  Select the type's mapping (Section 6).

   3.  Form the entry's cells (Section 3.1).

   4.  For each cell, populate the input variables (Section 3), resolve
       the mapping, verify the trust-anchored subject.id (Section 8),
       and add the resulting evaluations to the batch in place of the
       evaluation [ISSUANCE] would form for that cell.

   The AS then sends the batch, including the gate tuples [ISSUANCE]
   defines, and composes the result as [ISSUANCE] defines, treating a
   cell as permitted only if every evaluation the mapping produced for
   it is a permit.  The response shaping, no-broadening, and structural-
   check rules of [ISSUANCE] are unchanged.

9.2.  Resource PEP

   When an RS receives a call it authorizes under this binding, it MUST:

   1.  Validate the access token as it otherwise would.

   2.  Project the call onto an entry and a cell (Section 3.2).

   3.  Determine whether the token's authorization_details cover the
       projection, using the details the AS made available to it
       (Section 9 of [RFC9396]).  If they do not, the RS SHOULD answer
       with the remediation challenge of [RARMETA], built from the
       projection, and MUST NOT perform the call.

   4.  Select the type's mapping, populate the input variables, resolve
       the mapping, and verify the trust-anchored subject.id.

   5.  Send the constructed request to the PDP and permit the call only
       if every decision is a permit.

   6.  Before performing the call, confirm that the call's projection is
       unchanged from the one evaluated, as COAZ-MCP requires of a
       message, and re-evaluate or refuse it otherwise.

   Step 3 asks whether the token covers the call; step 5 asks whether
   policy permits it.  Both are required.  A token is evidence of what
   was granted at issuance; it is not evidence that the call, as made,
   is permitted now.

10.  Error Handling

   The framework's three categories are reported as follows.

   +===================+===============================+==============+
   | Category          | Issuance PEP                  | Resource PEP |
   +===================+===============================+==============+
   | Mapping error     | invalid_authorization_details | HTTP 500     |
   |                   | [RFC9396]                     |              |
   +-------------------+-------------------------------+--------------+
   | Authorization     | As [ISSUANCE] defines for     | HTTP 403     |
   | denial            | denied cells and gates        |              |
   +-------------------+-------------------------------+--------------+
   | PDP communication | As [ISSUANCE] defines: HTTP   | HTTP 503     |
   | error             | 503 with Retry-After          |              |
   +-------------------+-------------------------------+--------------+

                                 Table 3

   A mapping error at the Issuance PEP is reported as
   invalid_authorization_details because the entry, as received and
   enriched, cannot be evaluated; the client can do nothing with it but
   change the entry.  An AS MUST NOT relay the text of a mapping error
   to the client, for the same reason [ISSUANCE] forbids relaying PDP
   reasons.

   A denial at the Resource PEP of a call the token covers is answered
   with HTTP 403 and not with a remediation challenge: no token would
   change the decision.  An RS MAY include an error value as [RFC6750]
   allows, and MUST NOT include PDP reasons.

11.  Guidance for Mapping Authors

   This section is non-normative.

    +================+=====================+==========================+
    | The member is  | Put it in           | Example                  |
    +================+=====================+==========================+
    | An entity the  | resource (type and  | creditor_account:DE02... |
    | decision is    | id)                 |                          |
    | about          |                     |                          |
    +----------------+---------------------+--------------------------+
    | The specific   | resource.id, from   | customer:c-77            |
    | resource, when | identifier          |                          |
    | the entry or   |                     |                          |
    | call names one |                     |                          |
    +----------------+---------------------+--------------------------+
    | A quantity or  | action.properties   | {"amount": "123.50",     |
    | parameter of   |                     | "currency": "EUR"}       |
    | the act        |                     |                          |
    +----------------+---------------------+--------------------------+
    | A second       | A second evaluation | a debit of the source    |
    | entity the act |                     | and a payment to the     |
    | touches        |                     | payee                    |
    +----------------+---------------------+--------------------------+
    | A filter the   | resource.properties | a sensitivity filter on  |
    | client placed  |                     | a records request        |
    | on its request |                     |                          |
    +----------------+---------------------+--------------------------+
    | An assertion   | subject.properties  | a practitioner role      |
    | about who is   | or context          |                          |
    | asking         |                     |                          |
    +----------------+---------------------+--------------------------+

                                  Table 4

   Entities belong in the five-tuple because every PDP, including one
   that reasons over relationships, can use them.  A quantity does not:
   an amount has no identity and no relationships, and a relationship-
   based engine takes such a value as request context for a condition
   rather than as an object.  Section 5.3.1 of [AUTHZEN] provides for it
   directly: action properties "can include ... parameters of the action
   that is being requested."

   Do not reduce a value the policy might compare into a category in the
   mapping.  A mapping that sends "sensitivity": "high" for any amount
   over a threshold lets the PDP distinguish small payments from large
   ones, but not 25,000 from 60,000.  COAZ-MCP's discussion of
   authorization granularity applies equally here: an input a mapping
   does not project is not evaluated by the PDP.

   A filter the client places on its request (a set of sensitivity
   labels, say) exists in the entry but not in a call, so the AS and RS
   will see different properties for it.  That is expected and is one
   reason decision-critical inputs belong in the five-tuple.

   An assertion about who is asking, carried in an entry, is client-
   supplied and untrusted.  The AS has to verify it against an
   authoritative source; the mapping cannot make it trustworthy.

12.  Security Considerations

12.1.  Trust in the Type Definer

   A declared mapping determines what the PDP is asked.  A mapping that
   omits a decision-critical member, or projects it lossily, yields
   permits that do not reflect that member.  The AS adopts a mapping as
   configuration, and the trust it places in the type definer is the
   same trust it already places in the type's schema; deployments SHOULD
   review a mapping when adopting a type, as they would review the
   schema.

   A type definer that is also the RS addressed by the resulting token
   can, by a poor mapping, only weaken tokens addressed to itself,
   provided the AS restricts each token's audience to the evaluated
   resource as [ISSUANCE] requires.

12.2.  Remediation Entries Are Client-Carried

   The remediation entry passes through the client, which can alter it
   before requesting a token.  The AS evaluates the entry it receives,
   so an altered entry yields at most a token for what the altered entry
   describes, and only if policy permits that.  When the call is
   retried, the RS projects it afresh and checks both coverage and
   policy, so a token for an altered entry does not cover the original
   call unless the alteration was immaterial to it.

12.3.  Staleness

   A permit at issuance holds for the life of the token, and policy or
   relationships can change in that time.  The Resource PEP's evaluation
   on each call is what bounds the consequence.  This binding does not
   make an issuance decision a substitute for a decision at the RS.

12.4.  Fail-Closed Enforcement

   As the framework requires, a mapping error, a denial, or a PDP
   communication failure results in the cell, and therefore the call or
   the corresponding part of the grant, being refused.

13.  IANA Considerations

   This document has no IANA actions.

   [RARMETA] does not establish a registry for the members of an
   authorization details type metadata object.  Should it establish one,
   authzen_mapping (Section 6) is a candidate for registration there.

Appendix A.  Relationship to Other Specifications

A.1.  COAZ Framework and COAZ-MCP

   This document is a binding of [COAZFW] and follows the structure of
   [COAZMCP].  It reuses COAZ-MCP's mapping location, the tool input
   schema, as its second selection step, and its params variable, so
   that a tool's mapping can be used unchanged.

A.2.  AuthZEN Profile for OAuth 2.0 Token Issuance

   [ISSUANCE] defines the issuance decision this binding plugs into: the
   batch, the gate tuples, the cell decomposition, and how decisions
   shape the token.  This binding replaces only the per-cell projection,
   and only for types that declare a mapping.  Its default mapping is
   that projection.

A.3.  OAuth 2.0 RAR Metadata and Error Remediation

   [RARMETA] defines the types metadata endpoint where a mapping is
   published, and the remediation challenge whose entry this binding
   builds from the RS's projection.  It defines no consumer of the types
   metadata within its own flow; this binding adds two.

A.4.  OAuth 2.0 Authority Metadata

   [AUTHMETA] publishes, in protected resource metadata [RFC9728], what
   the actions of a scope or authorization details type mean.  That is
   information a PDP can use when answering; a mapping is how a PEP
   forms the question.  The two are complementary and independent.

Appendix B.  Open Issues

   This section is to be removed before publication.

   1.  Should the default mapping use identifier as resource.id when it
       is present?  Types built only from common data fields would then
       get instance-level questions at the RS without a declared
       mapping.  The default can only use the type as resource.type, so
       a collection and its members would share a type and differ only
       by identifier.

   2.  [RARMETA] has no extension point for type metadata members, so
       authzen_mapping has no registered home.

   3.  A type that carries its multiplicity in a type-specific array
       (Section 2.1 of [RFC9396], Figure 4) cannot be decomposed: the
       framework forbids an expression from setting the number of
       decisions, and even a binding-defined fan-out would leave the AS
       unable to rebuild a narrower array from the permitted items
       without knowing the type.

   4.  Should the mapping be able to name the claims it requires of the
       prospective token, instead of relying on optional selection?
